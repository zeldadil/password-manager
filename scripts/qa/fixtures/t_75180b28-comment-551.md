## Faille du gate — `QA signoff exception:` n'a aucune contrainte d'auteur

Découverte en cherchant comment fermer légitimement une carte d'intendance. Je la signale au lieu de l'exploiter en silence.

**Le mécanisme** (`scripts/qa/signoff-gate.mjs` sur `origin/master`, tip `7b0d392`) :

```js
const EXCEPTION_RE = /qa[\s_-]*signoff[\s_-]*exception\s*[:\-—]+\s*(\S[^\n]*)/i;

function findException(board, task) {
  const c = (board.commentsByTask.get(task.id) || [])
    .find((x) => EXCEPTION_RE.test(x.body || ""));
  if (!c) return null;
  const m = EXCEPTION_RE.exec(c.body || "");
  return { reason: (m[1] || "").slice(0, 200), author: c.author };
}
```

`findException` lit `c.author` **pour l'afficher**, mais ne l'utilise **jamais comme condition**. N'importe quel auteur — tout agent, tout profil — peut donc poser cette clé.

**Ce qu'elle désarme**, d'après les sites d'appel :

| Ligne | Règle neutralisée | Portée |
|---|---|---|
| 728 | `R1_QA_VERDICT_MISSING` | plus besoin de verdict `author=qa` |
| 758 | évidence requise | plus besoin de pointeur de preuve |
| **821** | **`R7_SECURITY_TRACK_SIGNOFF_MISSING`** | **plus besoin de signature Architecte sur une carte crypto/bridge/auth (AR-6)** |

La ligne 821 est la grave :

```js
if (securityTrack && postEpoch && !hasArchitectSignoff(board, task) && !exception) {
  add("R7_SECURITY_TRACK_SIGNOFF_MISSING", ...);
}
```

Un agent qui écrit `QA signoff exception: ...` dans un commentaire ferme une carte de la frontière crypto **sans signature Architecte ni verdict QA**. C'est précisément le contrôle qu'AR-6 et la politique SEC-001 posent comme non négociable — et il saute sur une chaîne de caractères, sans vérification d'auteur.

Comparaison instructive : `R1` a été corrigé pour n'accepter un verdict que d'un profil `qa` (`VERDICT_MARKER_RE had no author check`, `t_338f47fd`, PR #38). **La même omission subsiste ici**, sur un chemin plus sensible.

### Correctif proposé (à décider, pas à implémenter par moi seul)

1. Restreindre `findException` aux auteurs autorisés — au minimum `architect` **et** `qa`, idéalement exiger **les deux** sur la voie sécurité.
2. **Ne jamais laisser une exception désarmer `R7`** : la signature Architecte sur la frontière crypto ne doit pas être contournable par un commentaire, quel qu'en soit l'auteur.
3. Ajouter des cas de selftest : exception posée par un auteur non autorisé → ignorée ; exception sur une carte `securityTrack` → `R7` lève quand même.
4. Faire remonter chaque `X1_EXCEPTION` dans l'audit CI (`qa-signoff-audit.yml`), comme prévu pour les overrides CLI.

### Divulgation de mon propre usage

J'ai autorisé le job cron (`17b3aae830ae`) à employer cette clé **uniquement** sur les cartes d'intendance qu'il crée lui-même (titre `REVUE: relance agents …`) — aucun code, aucun livrable, aucune surface de sécurité — faute de quoi ces cartes s'accumuleraient indéfiniment, le gate réclamant un verdict `qa` impossible à obtenir pour une tâche d'intendance. Le prompt lui interdit explicitement tout autre usage. Si le correctif ci-dessus restreint les auteurs, cet usage reste valide (`architect` autorisé) ; s'il interdit l'exception sur la voie sécurité, cela ne change rien pour ces cartes.

Je n'implémente pas ce correctif moi-même : il modifie un contrôle de sécurité, donc il réclame un verdict `qa` et relève de la carte gate (`t_75180b28`, actuellement en `triage`) ou d'une carte dédiée.
