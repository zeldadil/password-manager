## CI card: wire the QA sign-off gate board audit as a scheduled CI job

**Parent:** t_33dcad7d (architect decision: audit belongs in CI as a scheduled job, not a per-PR required check)

**Decision context (read first):**
- The board audit (`node scripts/qa/signoff-gate.mjs audit`) is a board-wide policy/retro detection tool, not a per-PR code-quality gate.
- The real enforcement is already the `pre_tool_call` hook in all 7 profiles — a card cannot reach `done` without verdict + evidence regardless of CI.
- `.github/workflows/ci.yml` is an active collision hotspot across QA-001b/c/d/g, so this card must **not** edit `ci.yml` in a way that conflicts with those cards.
- Decision recorded in `docs/decisions/qa-signoff-gate-followups-t_33dcad7d.md` §CI wiring.

**What to build:**
- Add a **scheduled** (cron) job — NOT a `pull_request`/`push` required check — that runs `node scripts/qa/signoff-gate.mjs audit --repo ${{ github.workspace }}` against the default board and posts the result as a comment on a tracked issue or as a workflow summary.
- The job must not be listed as a required status check on `master` (that would make it a per-PR gate, which is not the intent and would collide with the hotspot).
- If and when a release-track / non-default board exists, the same job (or a variant) runs `audit --db <path>` against it — but no non-default board exists yet, so scope this card to the default board only.
- Re-use the existing `install-lockfile` → setup pattern from `ci.yml` so the job has a Node + pnpm environment and the repo checked out; the gate script is already at `scripts/qa/signoff-gate.mjs` and has zero npm dependencies.

**Acceptance criteria:**
1. A new scheduled CI job (`qa-signoff-audit`) exists in `.github/workflows/ci.yml` (or a dedicated workflow file if the team prefers to keep the hotspot file untouched) that runs on a weekly cron and on `workflow_dispatch`.
2. The job runs `node scripts/qa/signoff-gate.mjs audit --repo <repo-root>` and surfaces the pass/fail counts + any FAIL cards in the workflow summary or a posted comment.
3. The job is **not** added as a required status check on `master` (no branch-protection change).
4. The job does not alter the existing per-PR job graph (`install-lockfile → lint-typecheck → unit → integration → e2e → dependency-audit → secret-scan → build`) — no `needs:`, no new `pull_request` trigger blocking merges.
5. Evidence attached to this card: a screenshot or copy of the workflow file diff + a successful `workflow_dispatch` run URL (or a note that the repo is not yet visible to GitHub Actions and the diff is the deliverable).

**Out of scope:** retrofitting pre-epoch cards (that's a separate QA retro card if the team wants it); non-default board audit (deferred until such a board exists); changing the gate script (owned by `qa` on the gate card itself).
